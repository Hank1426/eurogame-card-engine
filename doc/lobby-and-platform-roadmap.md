# 下一阶段：游戏大厅、对局库与平台扩展

分析日期：2026-11-04。依据当前 `320fff7` 的仓库实现和已有验收记录。本文是开发建议，不表示这些功能已实现，也不改变既有方舟完整版本的验收标准。

## 结论

下一次增量建议优先完成游戏目录注册、多对局存储和大厅导航，同时继续方舟人工规则验收。UI 已有中央地图与底部操作台，接下来最有收益的改进是把工作台变成能管理多款游戏、多局实验和多种策略的稳定入口。

提前设计游戏 / 对局 / 座位 / 运行模式的边界，能够减少后续新增原创游戏、地图、AI 和联网房间时的修改范围。首期仍运行在浏览器内，不为了预留联网先建设账号、匹配队列或服务器。

## 当前实现与扩展障碍

| 现状与代码依据 | 扩展时的影响 | 优先级 |
|---|---|---|
| `MatchLobby.tsx` 的 `MatchSettings.game` 是两款游戏的联合类型，界面通过 `isDemo` 分支绘制规则 / 人数 / 地图 | 每加一款游戏就改同一个大厅，不能靠增加游戏目录项接入 | 高 |
| `App.tsx` 的 `startMatch`、`importSave`、路由和保存逻辑分别判断游戏 | 创建、继续、导入等入口容易出现行为差异；类型关联也分散 | 高 |
| `storage.ts` 只有 `saves` 存储，使用 `current` 和 `ark-current` 两个槽位 | 同款游戏只能保留一局；新建替换旧槽，不适合多种子 / 多地图 / 多策略实验 | 高 |
| 应用启动就 `importArchive` 两款游戏的存档，导入会从头回放每条命令 | 进入大厅承担规则恢复成本；扩展成对局库后会随历史数量增长 | 高 |
| `App.tsx` 与 `ArkTable.tsx` 各自安排 AI 定时器，人类固定为 `p1` | 更换策略、异步计算或接入远端运行时需调整牌桌；先抽出生命周期和座位定义更稳妥 | 中 |
| 原创模拟器直接依赖 Demo，方舟模拟使用独立脚本 | 新游戏还要复制运行循环与报告格式，平台复用证据不足 | 中 |
| `GameModule` 已隔离规则，`Session` 已包含版本、配置、种子、命令与分支 | 可直接复用，不需要重新设计规则核心 | 已具备 |
| 存档的 `branch.id` 普通对局都是 `main`，`gameId` 是游戏类型 ID | 两者均不能作为独立对局 ID，须在应用外层新增 `matchId` | 高 |
| 牌桌组件有懒加载，但主入口直接导入两款游戏规则；大厅也导入方舟地图模块 | 页面组件拆分不等于游戏模块按需加载；要先加载目录，选定游戏才加载规则 | 中 |
| 大厅游戏卡片较大，左侧导航同时包含创建、牌桌、规则、素材和实验 | 两款游戏可用，增加到六款会显得冗长；普通游玩和研究工具需更清楚组织 | 中 |
| 全牌库 235 条已接入，仍标记 `experimental`，逐卡复核和十局人工试玩未完成 | 更丰富的大厅不能视为方舟正式完成；必须显示当前适用范围与验收状态 | 高 |

## 大厅的产品结构

建议顶层保留三个主要目的地：“游戏大厅”“我的对局”“实验室”。对局内仍使用自己的专注布局，保留“返回大厅”入口。规则、素材、覆盖矩阵与模拟工具放到实验室或游戏详情的上下文入口，不占据所有游玩页面的主导航。

### 游戏大厅

桌面布局从上到下：

1. 一个紧凑的“继续上次对局”区，最多展示最近两局；更多对局进入对局库。
2. 游戏目录网格，每卡显示名称、自有封面、支持人数、玩法时长的估算或范围、可用模式与成熟度。
3. 点击游戏进入对应详情 / 创建面板：简介、胜负条件、支持范围、人数、地图 / 规则预设、AI 策略与开始按钮。

在 1440 宽的大厅可考虑三列游戏卡，每卡宽约 260–320 px、高约 220–280 px。实际按三种桌面尺寸验收后调整，不把固定像素当作最终设计。两个游戏时无需搜索框；达到约八个游戏再增加搜索和分类，避免目录还很小时先铺满筛选器。

游戏卡不承载完整规则和所有设置。创建面板独立开合；关闭返回目录时保留选项草稿。复杂地图可以使用名称 / 特性卡片，人数与模式使用简短选择按钮。高级种子、固定牌序和实验参数收在“高级 / 实验设置”中。

Demo 作为“原创 / 引擎示例”分类中的正常条目，不再让整个大厅围绕“Demo 还是方舟”二选一组织。

### 我的对局

对局列表优先使用紧凑行或小卡，而不是把历史对局都铺成大型封面。每条记录包含游戏、标题、状态、地图 / 预设、人数、进度、更新时间与继续按钮。

首期支持：继续、重命名、归档、复制实验局、导入、导出；已结束对局可查看结果和回放。归档保留文件和恢复入口，不等同于删除。

“等待你选择”“AI 暂停 / 错误”“版本不兼容”需要与一般暂停区分。方舟没有固定轮数，进度显示回合 / 休息次数，不能沿用 Demo 的轮数百分比。列表摘要由游戏适配器生成，公共 UI 不推测规则状态。

新建同款游戏获得新的 `matchId`；不覆盖旧局。导入相同文件默认作为新对局，可提示相同内容，但不能用相同种子判定重复，因为不同命令会产生不同对局。

### 实验室

入口保留规则覆盖、参考资料、素材、地图交互实验和模拟；逐步增加“加载验收场景”“策略对比”“参数实验”。普通大厅不出现数据库、哈希、修订号等工程字段，实验详情需要时再展开。

## 技术分层：提前准备的最小结构

建议目录：

```text
apps/web/src/
  catalog/       游戏元数据、能力与按需加载入口
  lobby/         游戏目录、详情与创建面板
  matches/       对局库、摘要、运行时元数据
  persistence/   IndexedDB 存储、旧槽迁移、写入与冲突处理
  runtime/       本地命令执行、AI 生命周期、运行状态
  games/demo/    Demo 网页适配器与独立牌桌
  ark/           方舟网页适配器与独立牌桌
  laboratory/    场景、覆盖、素材、模拟入口
```

不要求一开始把所有目录全部拆完。先提取目录 / 存储 / 启动三个边界，之后按真实职责迁移。

### 1. 游戏目录与适配器

轻量目录只含稳定 ID、名称、简介、人数范围、可用模式、成熟度和按需加载函数。浏览目录时不导入整个规则模块、AI 或牌库。

每个网页游戏适配器负责：

- 关联自己的 `GameModule`，保留配置、命令、视图和结果的 TypeScript 类型；不要把规则层统一降成 `any`。
- 提供默认设置、规则预设、地图选项及必要的配置 UI。
- 创建 / 导入对局，生成该游戏特有的进度和结果摘要。
- 提供规则页、牌桌组件、AI 策略清单与能力声明。

公共大厅以统一的目录与摘要交互；各游戏配置仍由对应适配器及 `parseConfig` 校验。不要为了自动画所有设置而建设复杂表单 DSL。一个原创游戏用资源转换，方舟用地图和五行动，这些差异应留在游戏模块和牌桌里。

能力声明必须具体：例如 `ai`、`supportedPlayerCounts`、`maps`、`replay`、`scenarios`；联网未实现时不显示可点的匹配按钮。未知游戏 ID 导入失败并说明原因，不默认走 Demo 导入。

### 2. 对局外层信息与存档

现有引擎存档保持原协议。新建外层信息记录：

```text
matchId、gameId、标题、createdAt、updatedAt
status、运行模式、座位配置、AI 策略 ID / 版本
engine / rules / content 版本、规则预设
当前修订号、游戏摘要、存档位置、归档状态
```

`matchId` 和时间由应用层生成，不写入确定性规则计算。游戏状态、规则种子和命令仍由 `Session` 管理。座位配置与 AI 策略属于运行方式，不能让 UI 直接修改规则状态。

首先可把 metadata 与 archive 保存为同一条 IndexedDB 记录，列表读取轻量摘要；也可使用 metadata / archives 两个 store，但每次必须同事务提交，不能出现列表修订与存档修订不一致。

旧 `current` / `ark-current` 迁移到独立对局 ID，迁移幂等，保留旧原始记录到迁移验证完成。列出历史时不完整回放；只有继续某局时才加载该游戏并通过 `importArchive` 严格验证。版本不兼容的文件仍可导出，不悄悄套用新规则。

写入必须绑定本次对局 ID 和修订号，不能在异步保存完成时使用已经切换的新 active ID。默认同一对局只允许一个标签页执行命令；跨页可用通知 / 所有权锁让其余页面进入只读，保存事务再检查预期修订，避免两个页面交替覆盖。

本地对局库不会自动跨设备同步，导出文件仍是首期备份方式。不能把 IndexedDB 中的“历史”误称为云存档。

### 3. 统一启动与运行时

大厅启动流程：

```text
选择游戏 / 预设 → 校验能力与配置 → 载入模块
→ 创建引擎 Session → 创建新 matchId → 原子保存
→ 打开该对局 → 本地运行时驱动人类与 AI
```

路由可仍使用 hash：`#/games`、`#/games/ark-nova`、`#/matches`、`#/matches/<id>`、`#/lab`。现有 `#/lobby` / `#/ark` / `#/table` 保留兼容跳转，避免已有链接和测试入口立即失效。

运行时先做具体的本地实现，统一命令提交、当前玩家视图、AI 执行状态、错误重试与销毁。牌桌调用运行时提交，不直接承担定时器 / 保存 / 网络生命周期。离开对局默认暂停本地 AI；切换对局取消旧计算，迟到结果通过 matchId、修订与 request ID 丢弃。

联网预留一个可替换的运行时边界即可，不要求当前实现远端适配器。未来远端客户端只拿自己可见的视图和允许动作，不能把完整存档、随机数、对手手牌发送到每个客户端再靠 UI 隐藏。

### 4. AI 与计算体验

策略 ID / 版本先统一，之后提供“随机合法”“基础启发式”等真实不同策略。AI 动画延迟只属于体验设置，不能用等待更久表示更强难度。

规则稳定后再实现更强策略。用固定种子 / 座次、双方交换座位、独立策略随机数进行比较，统计自然终局比例、步数、得分与胜率；不只靠随机模拟样本宣称平衡。

随着导入与策略计算变重，将完整回放、模拟和 AI 搜索放入 Web Worker。Worker 需要取消、修订校验和完整错误回传；先测量主线程阻塞，再决定迁移哪些任务。浏览大厅不应等待恢复所有存档。

## 下一步工作的排序

| 工作 | 推荐时间 | 价值与验收 |
|---|---|---|
| 大厅目录注册＋多对局库＋启动流程 | 下一次增量 | 新建同游戏两局都能继续，添加游戏不复制大厅分支，旧存档迁移保留 |
| 方舟逐卡复核 / 人工试玩记录 | 同期持续推进 | 跟踪具体规则差异；至少十局人工完整试玩，问题变成回归案例 |
| 本地运行时与 AI 策略标准化 | 对局库后 | Demo / 方舟共享生命周期，切换对局与异步结果不串局 |
| 规则回放 / AI Worker 与性能指标 | 实测后 | 大厅启动只读摘要，长回放不阻塞页面，操作和取消正常 |
| 场景库与策略实验报告 | 本地管理稳定后 | 一键加载验收案例、记录失败种子和对比结果 |
| 第二款完整原创小型游戏 | 按既定复用验收推进 | 真正检验目录、运行时、存档、模拟与机制复用；不是再添一张展示卡 |
| 地图 3–8 / 更多人数 / 单人 | 分独立范围实现 | 每个范围补规则来源、场景与 AI 验收；不当作单纯人数 UI 配置 |
| 朋友房间 | 明确需要异地游玩后 | 两浏览器受控视图、服务器校验、断线恢复与持久化 |
| 自动匹配、账号社区、排行榜 | 房间服务稳定之后 | 有真实使用与部署需求再扩展 |

如果最主要目标是增强方舟游玩，顺序可以改为：基础存档保护 → 人工验收工具 → AI 与规则修复 → 地图 3/4。多游戏大厅依然复用相同目录与对局信息边界。

## 首个增量的具体工作包

建议目标：“可以保留、找到并继续多局游戏，新游戏有标准接入口”。工程估算 35–50 小时，包含迁移、实现、浏览器回归和文档；尚未拆任务验证，按个人加 AI 视作规划区间。每周 10–15 小时约需 3–5 周，可拆两次可体验发布。

| 子包 | 估算 | 内容 |
|---|---:|---|
| 目录与适配器 | 6–9 小时 | Demo / 方舟元数据、能力、配置与懒加载入口；创建 / 导入明确路由 |
| 多对局与旧槽迁移 | 12–17 小时 | matchId、摘要、原子保存、迁移、兼容性提示、迟到保存防串局 |
| 大厅与对局列表 | 9–13 小时 | 紧凑继续入口、游戏卡、独立设置、继续 / 重命名 / 归档 |
| 回归与发布 | 8–11 小时 | 正常与损坏迁移、两个同游戏对局、切换保存、AI 生命周期、构建与 Pages |

第一发布可只包含“新建不覆盖＋对局列表”；第二发布再完成目录与设置面板重构。不要一次同时改规则、牌桌、存档格式、AI 和网络。

验收清单：

1. 新建方舟 A 与 0 两局，双方进度不同，来回继续与刷新各自一致。
2. 新建 Demo 两局，继续 / 方舟切换不串局，不误导出另一款游戏的文件。
3. 原有两个槽位迁移一次完成；失败保留原文件与可导出入口，刷新不重复生成迁移记录。
4. 历史列表在不恢复所有命令的情况下显示；点击继续后才校验完整存档。
5. 拒绝未知游戏、无效配置和不兼容版本；归档可恢复。
6. 同局第二标签页不能覆盖第一标签页的较新修订；切换对局后迟到 AI / 写入不影响新对局。
7. 大厅在三种桌面尺寸可浏览；创建设置不塞满所有卡片，没有假联网入口。
8. 模块接口以 Demo / 方舟真实接入验证；新增实验模块只改目录 / 适配器，不修改通用存储和规则核心。

## 联网的未来方案

GitHub Pages 继续作为静态前端。房间服务单独部署，Node 运行同一规则模块；第一步做邀请链接 / 房间码，让朋友加入明确的房间，再考虑自动匹配。

服务器绑定用户到座位，验证命令 ID、操作者和修订号，保存命令与快照，并只分发每位玩家可见状态。需要处理创建 / 等待 / 进行 / 完成状态、版本固定、重连快照、序列号和服务器 AI。引擎已有修订拒绝是有用基础，但目前重复 ID 的拒绝不等于网络重试完成：远端需定义重复请求返回原结果还是状态确认。

房间服务还需自己的持久化、部署和访问控制，不能借 Pages 的静态托管冒充权威对局。首期可以预留 `transport` 与 seat ownership 数据模型，暂不运行这些服务。

## 当前不建议先建的内容

- 通用脚本语言、任意第三方规则插件、可视化规则编辑器。
- 账号好友、聊天、天梯与大型自动匹配。
- 给所有桌游统一的地图 / 行动 / 计分 UI；共用外壳，布局由游戏适配器提供。
- 没有实测需求的复杂数据库、服务拆分或云同步。
- 把“原作全牌库已录入”直接升级成正式完整版本，或把“新增目录条目”当作引擎复用验收。

优先建设会立即用于两款现有游戏的能力；随着第二款原创游戏与真实联网需求出现，再扩大基础设施。
