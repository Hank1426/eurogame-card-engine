# 游戏目录与多对局库验收

日期：2026-11-04。首批范围为统一游戏目录、多对局保存、继续、重命名、归档 / 恢复、导入导出、旧存档迁移与本地操作隔离。

## 用户流程

- 大厅保留两条最近对局摘要，“查看全部对局”进入对局库。
- 每次新建 / 导入获得新的对局 ID，同款游戏和相同种子不会覆盖旧局。
- “我的对局”按最近保存排序，显示游戏、地图、人数、轮次 / 回合、等待谁操作和更新时间。
- 可继续、重命名、导出、归档与恢复；归档保留存档，不做删除。
- 不兼容或损坏的旧存档保留原始文件，能在对局库原样导出；恢复时说明错误。
- 离开牌桌暂停本地 AI。返回同一局可继续；切换其他对局销毁旧牌桌，迟到更新通过 runtime 身份检查拒绝。
- 同局第二标签只读。第一标签关闭后可以“重新载入并尝试接管”，接管读取最新存档，不能抢占仍被使用的锁。

## 数据与规则边界

规则核心、Session 存档格式、规则版本和卡牌内容保持原有协议。应用外层 `MatchInfo` 管理 ID、标题、时间、归档、运行模式、座位与 AI 策略标识。

IndexedDB 升级至版本 2：`saves` 保留旧槽位；`matches` 保存轻量元数据；`archives` 保存原始引擎文件；`settings` 保存迁移标记和各游戏最近对局。

新建 / 保存的摘要与存档同事务提交。每次保存绑定具体对局 ID 与写入版本，事务内部再检查版本和游戏 ID，避免并发覆盖。异步写入串行执行，切换对局前等待旧写入完成；保存失败冻结当前对局写入，内存进度仍可导出。

迁移只读取旧 `current` / `ark-current` 摘要，不执行规则恢复；迁移标记与新增记录同事务写入，重复运行不会新增重复迁移局。旧两个槽位原文不删除，不再作为新对局覆盖目标。

浏览大厅 / 对局库只读取轻量摘要；继续某局时才根据 gameId 加载适配器并执行严格 `importArchive` 验证。旧链接 `#/lobby`、`#/ark`、`#/table` 与规则页保留，新增独立路由 `#/matches/<matchId>` 和对局库 `#/matches`。

网页适配器保持各游戏配置 / 命令 / 状态类型，公共目录只处理元数据、加载入口和 opaque runtime。方舟与 Demo 独立牌桌接入相同创建 / 恢复 / 保存流程；Demo 实验场景与调试分支创建新对局，不覆盖来源对局。未知 gameId 明确拒绝，不默认当作 Demo。

## 性能与兼容

大厅不直接导入游戏牌桌、AI 或方舟规则模块；正式构建分别生成 Demo / 方舟适配器分包，主入口由约 515 KB 降到约 369 KB（未压缩）。规则与牌桌载入都按用户进入的游戏进行。

本地写入所有权使用浏览器 Web Locks。若浏览器缺少该能力，按只读处理，仍可导出；当前桌面验收环境支持该 API。页面关闭释放锁，写入版本检查作为存储层的第二道冲突检查。

本批没有云同步、异地联机或第三方插件加载。目录接入口为仓库内开发，JSON 不执行任意规则代码。方舟仍是基础双人实验验收范围。

## 验收案例

1. 两局方舟 A / 0 与两局 Demo 共四个不同 ID，逐局继续、刷新、导出核对 gameId、种子和地图。
2. 相同种子再导入仍新建，重命名、归档与恢复不改规则状态。
3. 旧两槽迁移两局，刷新幂等，原槽原文保持；进入大厅不请求适配器，点击继续后才载入。
4. 损坏旧文件在对局库可原样导出，恢复失败不丢失原文；未知游戏导入不替换当前局。
5. 第二标签只读、无 AI 自动写入，关闭第一标签后读取其最新修订并接管。
6. 外部更新写入版本后旧页面不能覆盖存储，未保存内存进度可导出。
7. 切换新局暂停旧局 AI；返回旧局后才完成下一决策，新局修订保持不变。
8. 原有方舟与 Demo 规则、界面、保存恢复、回放、实验分支继续回归；三种桌面尺寸截图检查大厅与对局列表。

截图由 `pnpm ui:capture:library` 保存至 `.artifacts/library-ui/`。新增模型测试和八项浏览器测试分别位于 `apps/web/src/matches/model.test.ts`、`tests/e2e/match-library.spec.ts`。
